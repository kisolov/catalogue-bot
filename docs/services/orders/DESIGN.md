# orders — решения

## Заказ из корзины — одна транзакция в адаптере заказов

- **Решение:** `OrderRepository.create_from_cart` пишет заказ, позиции, остатки и корзину в одном `db_session`.
- **Альтернативы:** оркестровать в use case через `CartService` + `ProductService` + `OrderService` (несколько `db_session`, нет атомарности); Unit of Work поверх Pony.
- **Почему так:** всё в одной БД, а нужна атомарность и блокировка остатков; несколько независимых сессий оставили бы частичный заказ при сбое. Цена: адаптер заказов знает сущности корзины и товара.

## Смена статуса и возврат остатков — тоже в адаптере

- **Решение:** `set_status(order_id, status, restore_stock)` меняет статус и возвращает остатки в одной транзакции; правила (матрица переходов, кто может отменять) остаются в `OrderService`.
- **Альтернативы:** менять статус в сервисе, а остатки возвращать отдельным вызовом.
- **Почему так:** между двумя вызовами возможен сбой — заказ отменён, остатки не возвращены.

## Снимок цены и названия в позиции заказа

- **Решение:** `OrderItem` хранит `price` и `product_name` копией.
- **Альтернативы:** ссылка на товар и чтение цены из него.
- **Почему так:** цена и название товара меняются, а сумма заказа должна остаться прежней.

## Чужой заказ — 404, а не 403

- **Решение:** для неверного владельца заказ «не существует».
- **Альтернативы:** 403.
- **Почему так:** 403 подтверждает, что заказ с таким id есть; последовательные id иначе позволяют перебор.
