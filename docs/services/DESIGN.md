# Решения

Подробное обоснование — в [spec](../superpowers/specs/2026-09-28-backend-polish-design.md).

## Заказ из корзины — одна транзакция в адаптере заказов

- **Решение:** `OrderRepository.create_from_cart` пишет заказ, позиции, остатки и корзину в одном `db_session`.
- **Альтернативы:** оркестровать в use case через `CartService` + `ProductService` + `OrderService` (несколько `db_session`, нет атомарности); Unit of Work поверх Pony.
- **Почему так:** всё в одной БД, а нужна атомарность и блокировка остатков; несколько независимых сессий оставили бы частичный заказ при сбое. Цена: адаптер заказов знает сущности корзины и товара.

## Вход только через Telegram, `POST /users/` — только админ

- **Решение:** публичной регистрации нет, пользователь создаётся при первом входе через подписанный `initData`.
- **Альтернативы:** оставить открытый `POST /users/`.
- **Почему так:** открытый эндпоинт с полем `role` позволял выдать себе `admin`.

## Миграции при старте с учётом применённых

- **Решение:** таблица `schema_migrations`, каждый файл выполняется один раз.
- **Альтернативы:** initdb.d Postgres; Alembic.
- **Почему так:** перезапуск контейнера падал с `DuplicateObject`. initdb.d не переживает существующий volume; Alembic избыточен для одного файла, но переход на него возможен позже.

## Оплата вне объёма

Заказ создаётся в статусе `new`, платёжный шлюз — отдельный этап.
